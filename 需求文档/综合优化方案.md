# 第一部分：问题诊断

---

## 一、AI 对话性能问题

### 1.1 根因分析

```
当前流程:
  用户请求 → ChatMemory.get() [Redis LRANGE 0 -1 全量]
           → chatClient.call()   [全量历史作为上下文发LLM]
           → ChatMemory.add()    [Redis RPUSH]
           → saveMessages()      [DB INSERT ×2]
```

| 瓶颈 | 解释 |
|------|------|
| **上下文膨胀** | 50轮 = 10000+ token 发给 LLM，响应时间线性增长到 15s+ |
| **全量读取** | `LRANGE 0 -1` 无上限，100轮 = 100次 JSON 反序列化 |
| **用户消息双写** | `saveChatRecord()` 和 `saveMessages()` 各写一次 |
| **无超时** | `chatClient.call()` 无超时控制，AI 慢则挂死 |

### 1.2 影响量化

| 对话轮数 | Token 数 | 延迟 | 状态 |
|----------|---------|------|------|
| 5 轮 | ~1,000 | ~2s | 正常 |
| 20 轮 | ~4,000 | ~5s | 变慢 |
| 50 轮 | ~10,000 | ~15s+ | 不可用 |
| 100 轮 | ~20,000 | 超时 | 超出上下文窗口 |

---

## 二、健康评估性能问题

### 2.1 根因分析

```
assessmentData():
  LLM1(能力评估, ~5s) → LLM2(体检分析, ~10s) → LLM3(综合建议, ~8s)
  总耗时: ~23s（三次串行）
```

- LLM1 和 LLM2 数据互不依赖，可以并行
- Prompt 体积大（3000+ token 指令 + 报告全文）
- PDF 解析阻塞主线程
- 无结果缓存（重复提交重新走全流程）

---

## 三、存储架构问题

### 3.1 现状

| 数据类型 | 存储 | 问题 |
|---------|------|------|
| AI 对话历史 | MySQL `ai_message` + `ai_conversation` | 不支持全文检索，大量对话后查询慢 |
| 设备上报数据 | MySQL `device_data` | 时序数据无限增长，无过期策略 |
| 操作日志 | MySQL `sys_oper_log` | 同设备数据，无自动清理 |
| 对话记忆 | Redis List (String) | JSON 字符串反复序列化/反序列化 |
| 设备最新数据 | Redis Hash (String→JSON) | JSON 字符串序列化开销 |

### 3.2 目标架构

| 数据类型 | 当前 | 优化后 | 理由 |
|---------|------|--------|------|
| AI 对话历史 | MySQL | **Elasticsearch** | 全文检索、时序优化、自动过期 |
| 设备上报数据 | MySQL | **Elasticsearch** | 时序索引、TTL 自动清理、聚合查询 |
| 操作日志 | MySQL | **Elasticsearch** | 海量日志检索、自动归档 |
| 对话记忆 | Redis List(String) | **Redis Stack (JSON)** | 原生 JSON 存储、跳过序列化 |
| 设备最新数据 | Redis Hash(String) | **Redis Stack (JSON)** | 原生 JSON、RediSearch 结构化查询 |

# 第二部分：优化方案

---

## 四、AI 对话优化

### 4.1 滑动窗口 + 摘要策略

```
优化后 flow:
  chatMemory 维护最近 N 条消息 (N=10)
  超出部分 → LLM 生成摘要 → 注入 system prompt
  Redis LTRIM key -20 -1 (保留最近 20 条)
  总 Token 控制在 2000 以内
```

**改动文件**: `RedisChatMemoryServiceImpl.java`, `ChatController.java`

**预期效果**: 50轮延迟 15s → 5s (降低 67%)

### 4.2 超时 + 降级

| 改动 | 说明 |
|------|------|
| `ChatController.chat()` | 包装 `Future.get(30, SECONDS)` |
| 超时降级 | 返回 "AI 响应超时，请稍后重试" |
| 配置 | `ai.chat.timeout: 30000` |

### 4.3 消除重复写入

删除 `AiConversationServiceImpl.saveChatRecord()` 中的用户消息保存逻辑，统一由 `saveMessages()` 处理。

### 4.4 使用 Redis Stack JSON 优化 ChatMemory

```
当前:
  Msg对象 → JSONUtil.toJsonStr() → String → Redis List

Redis Stack 优化:
  Msg对象 → RedisJSON.set() → 原生 JSON 存储
  读取: RedisJSON.get() → 直接 Msg 对象
  跳过序列化/反序列化，支持 JSONPath 查询单条消息
```

## 五、健康评估优化

### 5.1 LLM 并行化（立即见效）

```java
CompletableFuture<AssessmentResult> f1 = 
    CompletableFuture.supplyAsync(() -> callLLM1(data));

CompletableFuture<MedicalReportResult> f2 = 
    CompletableFuture.supplyAsync(() -> { 
        downloadPDF(); parsePDF(); return callLLM2(report); 
    });

CompletableFuture.allOf(f1, f2).join();
String suggestion = callLLM3(f1.get(), f2.get());
```

**预期效果**: LLM1(5s) ∥ LLM2(10s) → max(5s,10s) = 10s, 总耗时 23s → 18s (降低 22%)

### 5.2 异步任务化（深度优化）

```
当前: POST assessmentData → 等待 23s → 返回结果

优化: POST assessmentData → 立即返回 taskId → 后台异步处理
      GET assessmentData/{taskId}/status → {progress, result?}
    
        进度推送: 保存数据 → 5% → 能力评估完成 → 40% 
                → 体检分析完成 → 80% → 综合建议完成 → 100%
```

**改动**: `HealthAssessmentServiceImpl` 新增 `@Async assessmentDataAsync()` + TaskStatus 表

### 5.3 Prompt 精简

| 改动 | 说明 |
|------|------|
| `getMedicalReportPrompt()` | 3000+ token → 1000 token |
| JSON Mode | 使用 `response_format: json_object`，删除冗余格式约束 |
| system/user 分离 | 规则放 system，数据放 user，减少重复 |

### 5.4 中间结果缓存

| 缓存 | Key | TTL |
|------|-----|-----|
| PDF解析 | `assessment:pdf:{md5}` | 1h |
| 能力评估 | `assessment:level:{id}` | 24h |
| 体检分析 | `assessment:medical:{id}` | 24h |

## 六、存储架构升级

### 6.1 Redis → Redis Stack 升级

**可行性**: ✅ 完全兼容。Redis Stack 是 Redis OSS 的超集，`redis/redis-stack:7.4.0-v1` 镜像直接替换。

### 6.2 设备数据 → InfluxDB（推荐）

**选型理由**：详见 `InfluxDB-vs-ES-存储选型对比.md`

| 对比 | InfluxDB | Elasticsearch |
|------|----------|---------------|
| 磁盘占用 | 1x | ~10x |
| 写入速度 | 百万点/秒 | 几千条/秒 |
| 时序聚合 | 原生窗口函数 | date_histogram |
| 自动过期 | Retention Policy 一行 | ILM + rollover 配置 |

```
设备数据设计:
  Measurement: device_data
  Tags:  iot_id, product_key, function_id
  Fields: data_value, location_type, physical_location_type
  Time:   alarm_time
  
  Retention: 90天自动过期
```

### 6.3 AI 对话历史 → Elasticsearch（推荐）

**选型理由**: AI 对话历史核心需求是**全文检索**。InfluxDB 无分词器、无高亮、无相关性排序。

```
索引: ai_messages-{YYYY-MM} (按月轮转)
ILM: 保留180天 → delete
```

### 6.4 操作日志 → InfluxDB

操作日志为时序事件，不需要全文检索，用 InfluxDB 更轻量。

### 6.5 最终组件清单

| 组件 | 用途 | 变化 |
|------|------|------|
| MySQL 8.x | 业务数据主库 | 不变 |
| Redis → Redis Stack 7.4 | 缓存+记忆+最新数据 | 升级 |
| InfluxDB 2.7 | 设备数据+操作日志 | 新增 |
| Elasticsearch 8.x | AI对话历史 | 新增 |
